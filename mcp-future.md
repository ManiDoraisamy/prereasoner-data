# MCP Implementation — v2 (reasoning in PreReasoner)

> **Audience: Claude Code.** Build spec for the version where PreReasoner derives the **reasoning
> plan itself** — not just the execution of each step. This is what makes the full auditability
> claim true. Verify current behavior against `runtime20/*`, especially the `/reason`
> view-stacking compositional reasoner, which already produces the view DAG internally. Code wins.
>
> **The one-line thesis this version delivers:** *both the reasoning and the execution are
> interpretable, because both are deterministically **derived** from the anchored representation —
> not generated by an LLM.* In v1 (`mcp-now.md`) the LLM decomposes the question inside its
> forward pass, so only execution is auditable. In v2 the decomposition becomes a derived,
> inspectable artifact.

---

## The core distinction (do not lose this)

There are two ways to make a reasoning plan "visible," and only one of them is auditable:

- **Generated-and-visible:** an LLM writes the plan (in Mermaid, Datalog, whatever). It is
  *readable* — you can inspect and reject it — but it can be **confabulated**: fluent, plausible,
  wrong. Same failure mode as generated SQL. This is NOT what v2 builds.
- **Derived-and-visible:** the plan is deterministically produced from PreReasoner's anchored
  representation (an extension of the existing view-DAG derivation), then **serialized** into a
  trained-on, renderable format. This is auditable-by-construction. This IS what v2 builds.

**v2 is a serializer of derived structure, never a generator of plans.** PreReasoner already
computes a view DAG inside `/reason` (e.g. `[world_join, world_filter, group_agg, topn]`). v2
exposes that derived DAG as a first-class, inspectable, executable artifact in a format humans and
tools already read. You are not adding "an LLM that writes Mermaid." You are adding "emit the DAG
we already derive, in a legible format."

## Architecture

```
User question
   │
   ▼
LLM orchestrator ──(parse NL, route, security, conversation)──┐
   │                                                          │
   │  calls PreReasoner ONCE for the PLAN                     │
   ▼                                                          │
PreReasoner: derive view DAG  ──serialize──▶  PLAN ARTIFACT   │
   │            (deterministic)              (Mermaid/Datalog) │
   │                                              │           │
   │  orchestrator (or PreReasoner) executes      │           │
   │  each step in the plan SEQUENTIALLY          │           │
   ▼                                              ▼           │
PreReasoner: execute step 1 ─trace─▶ ... ─▶ step N ─trace─▶ answer
```

**Call pattern (this is your stated v2 design, made precise):**
- **Simple / single-hop question:** orchestrator calls PreReasoner **once** — plan is trivial
  (one step), derive-and-execute together, as today.
- **Complex / multi-hop question:** orchestrator calls PreReasoner **for the plan first** (returns
  the Mermaid/Datalog DAG), then calls it **again per step** to execute each node auditable. The
  plan call is the new thing; the execution calls already exist.

Both the plan and each execution are derived, so both are auditable — the v2 claim.

## New MCP tool

### Tool: `prereasoner_plan`
The v2 addition. Takes a (possibly multi-hop) question + dataset, returns the **derived reasoning
plan** as a serialized DAG.

Input: `question`, `dataset_id`.

Output:
- `plan`: the derived view DAG serialized in the chosen format (Mermaid or Datalog — see selection
  below). Each node names a primitive (`filter`, `group_agg`, `topn`, `world_join`, …) and edges
  carry the dependency/order structure.
- `plan_render`: the human-viewable form (for Mermaid, the diagram source that renders directly in
  the UI — a flowchart of the reasoning the user can *see*).
- `steps`: an ordered/partially-ordered list of executable step handles the orchestrator feeds
  back to `prereasoner_query` (or a `prereasoner_execute_step`) one at a time.
- `derivation`: reason + alternatives + confidence for the decomposition itself (why these steps,
  what other decompositions scored lower) — so the *plan* carries the same audit metadata every
  other layer does.

The existing `prereasoner_query` (from v1) remains, now optionally driven step-by-step from a
`plan`.

## Plan format selection: Mermaid vs Datalog — investigate, then choose

The plan artifact should be **declarative, DAG-shaped, and well-represented in training data** so
it is legible and renderable — NOT because an LLM generates it (PreReasoner derives it), but
because a trained-on format is one humans and tools already read, and (for Mermaid) renders for
free. **Before committing, run the training-data investigation below** and pick one primary format
(the other can be a secondary lowering).

### The two candidates

- **Mermaid flowchart** — declarative, DAG-native, renders visually everywhere, heavily present in
  GitHub/docs/Qwen-Coder training data. Its text *is* its structure (parse tree = execution tree).
  Weakness: it is a *diagram* language with no execution semantics — node labels must name
  primitives your executor understands. Best as the **human-facing plan surface**.
- **Datalog** — the cleanest declarative target for **multi-hop / recursive / transitive** steps
  ("third person in gold tier", unbounded FK chains). Recursion and transitive closure are native.
  Present in training data (Soufflé, Datomic, CodeQL, logic-programming corpora) but **thinner**
  than Mermaid/Python. Best as the **executable lowering for recursive cases**.

### Investigation task (do this first, report before choosing)

Measure actual representation in the corpora that matter, rather than assuming:

1. **Stack / public code corpus (The Stack, GitHub):** count and sample files/blocks for each
   format. For Mermaid: fenced ` ```mermaid ` blocks + `.mmd`/`.mermaid` files, `flowchart`/`graph`
   directives. For Datalog: `.dl`/`.datalog` files, Soufflé `.decl`/rule syntax, Datomic query
   forms. Report: raw counts, rough proportion, and **diversity** (how many distinct
   repos/domains, not just volume — a format concentrated in one project is thinner than the count
   suggests).
2. **Qwen tokenizer coverage:** for each format's characteristic tokens (Mermaid `-->`, `[...]`,
   `flowchart TD`; Datalog `:-`, `.`-terminated rules, variable capitalization), check they
   tokenize cleanly (few tokens per construct, no pathological byte-splitting). A format the
   tokenizer fragments badly is worse to emit and worse to (if ever) parse.
3. **Legibility test:** render 5–10 of your actual view DAGs in each format by hand. Which reads
   more clearly *as a reasoning trace a non-expert can follow*? Mermaid's rendered diagram is a
   strong advantage here; Datalog is denser but exact for recursion.
4. **Dependency-structure fit:** confirm the chosen format can express your DAG's
   **non-sequential data dependencies** (the composition-order question — where one step consumes
   another's output, not just "next"). Mermaid edges must capture this; if some dependency can't
   be drawn as a simple flowchart edge, Mermaid is a *view* and the real executable is
   Datalog/JSON.

### Decision rule (apply after the investigation)

- If the investigation confirms Mermaid is far better represented and renders your DAGs legibly
  **and** captures the dependency structure: **Mermaid is the primary plan artifact** (the
  human/tool-facing surface), with an internal JSON-DAG as the executable and **Datalog as the
  lowering only for recursive/transitive steps** Mermaid can't execute.
- If multi-hop recursion turns out to dominate your target queries (SEC-filing / judicial
  multi-hop): weight Datalog higher as the executable, keep Mermaid as the rendered *view*.
- **Default expectation** (verify, don't assume): Mermaid as the derived, rendered plan surface;
  Datalog as the recursive lowering; existing JSON view-DAG as the executable intermediate. Three
  representations of one derived plan, each at the right layer — analogous to SQL-as-bytecode.

Whatever you choose: **the LLM never generates the plan format.** PreReasoner derives the DAG and
serializes it. The format choice is about *legibility and rendering*, not generation fluency.

## Executing the plan (both levels auditable)

Once the plan artifact exists:

1. Execute each node **sequentially / in dependency order**, each as an auditable step (existing
   `/reason` step execution, streamed to RTDB).
2. The user (or auditor) can inspect **two levels**: the **plan** (was this the right
   decomposition? — the Mermaid diagram / Datalog rules) and each **step** (did it compute
   correctly? — the SQL + resolution + trace).
3. Contrast with v1 in the UI/story: v1 showed only the executed steps; v2 shows *the plan that
   chose them*, derived and inspectable.

### The recursion boundary (carry from ROADMAP Phase D/E)

Multi-hop over bounded FK chains lowers cleanly. **Genuinely recursive / unbounded-depth** steps
(transitive closure) need a fixpoint — isolate them behind an explicit `closure(...)` primitive in
the plan, keep the iteration visible in the trace. For these, Datalog is the natural lowering
(recursion is native). This is where the format choice above interacts with the reasoning: the
recursive cases are exactly where Datalog earns its place.

## Carry-over invariants (from ROADMAP.md — do not relax)

- **Derived, not generated** — the whole v2 claim. The plan is a serializer of PreReasoner's
  derived view DAG. If at any point an LLM writes the plan, the auditability claim collapses to
  v1's.
- **No separate explainability agent.** If reasoning lives in PreReasoner and is derived, it is
  auditable by construction and needs no narrator. Proposing one is a symptom that reasoning has
  leaked back into the LLM.
- Every layer emits **reason + alternatives + confidence** — now including the **plan** layer
  (`derivation`: why this decomposition, alternatives, confidence).
- **Determinism where structure exists.** Plan derivation is deterministic. Do not make the
  decomposition a learned/generated step.
- **Orchestrator does selection/security/conversation; PreReasoner does reasoning + execution.**
  The moat is that the reasoning never leaves the auditable engine.

## Done when

- `prereasoner_plan` returns a **derived** (not generated) reasoning DAG for a multi-hop question,
  serialized in the chosen format, with a renderable view and per-decomposition audit metadata.
- The plan executes step-by-step, each step auditable, and a user can inspect **both** the plan
  and each step.
- The Datalog-vs-Mermaid investigation is documented (counts, tokenizer check, legibility,
  dependency fit) and a primary format is chosen with the recursive lowering identified.
- A recursive multi-hop question ("nth person in gold tier", a transitive FK chain) produces a
  plan whose `closure`/recursive step is explicit and whose fixpoint iteration is visible in the
  trace.
- Nowhere does an LLM generate the plan. The plan is derived and serialized; the LLM only
  orchestrates execution and speaks prose around the result.
