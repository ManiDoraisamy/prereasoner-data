# MCP Implementation — v2 (reasoning derived *inside* PreReasoner)

> **Audience: a developer who has read [`mcp-now.md`](mcp-now.md), plus Claude Code.** This is the build
> spec for the version where PreReasoner exposes the **reasoning plan itself** as a derived, inspectable
> artifact — not just the execution of each step. Everything here builds on the same engine described in
> `mcp-now.md` §0 (the `engine/` package; there is no `runtime20/`). **The code wins where this doc
> disagrees.** In particular, the plan-DAG this version *serializes* is the one
> [`engine/compose.py`](engine/compose.py) already *derives* — verify against it before building.
>
> **The one-line thesis v2 delivers:** *both the reasoning and the execution are interpretable, because
> both are deterministically **derived** from the anchored representation — not generated by an LLM.* In v1
> the LLM decomposes the question inside its forward pass, so only execution is auditable. In v2 the
> decomposition becomes a derived, inspectable artifact.

---

## 1. The core distinction (do not lose this)

There are two ways to make a reasoning plan "visible," and only one is auditable:

- **Generated-and-visible:** an LLM writes the plan (in Mermaid, Datalog, whatever). It is *readable* — you
  can inspect and reject it — but it can be **confabulated**: fluent, plausible, wrong. Same failure mode
  as generated SQL. **This is NOT what v2 builds.**
- **Derived-and-visible:** the plan is produced deterministically from PreReasoner's derivation, then
  **serialized** into a trained-on, renderable format. Auditable by construction. **This IS what v2
  builds.**

**v2 is a serializer of derived structure, never a generator of plans.** The engine already computes a
primitive-view DAG — see §2. v2 exposes that DAG as a first-class, inspectable, executable artifact in a
format humans and tools already read. You are not adding "an LLM that writes Mermaid"; you are adding
"emit the DAG we already derive, in a legible format."

---

## 2. What already exists (the DAG is real — go read it)

The decomposition v2 exposes is **not new work to invent** — it is already computed today. Grounding:

- **`engine/compose.py` → `ComposeEngine.run(tables, question, world=None)`** decomposes a question + one
  table into a **DAG of primitive views**, in a fixed analytics pipeline order (from the module docstring
  and `_plan`): *filters (exclusion, temporal) → aggregate → a derive (`yoy` / `running` / `share` /
  `divide`) → `having` → rank (`topn` / `sort`)*, standing on a `join` + `world_join` base.
- **Which composition *patterns* fire is read off the LEARNED primitive head**
  ([`engine/primitive_head.py`](engine/primitive_head.py) `PrimitiveReader`, weights in
  `engine/data/primitives.npz`); the concrete arguments of each view are filled deterministically. So the
  *shape* of the plan is derived from the anchored model, not hand-written and not LLM-written.
- **The primitives themselves are pure SQL view builders** ([`engine/primitives.py`](engine/primitives.py)):
  `filter_view`, `group_agg_view`, `yoy_view`, `topn_view`, `share_view`, `divide_view`, `running_view`,
  `join_view`, `world_join_view`. Op names: `filter`, `group_agg`, `yoy`, `running`, `share`, `divide`,
  `having`, `topn`, `sort`, plus the `join`/`world_join` base.
- **`engine/world_compose.py` → `ComposedWorldQuery`** stacks those views over the world base and
  **streams each one** to the trace as `views/{i}: {op, label, sql, columns, rows}` (see `mcp-now.md`
  §0.5). It delegates non-composed queries to `WorldQuery`.

So the derived DAG is already: computed (`ComposeEngine`), executed (on SQLite via the view builders, and
re-expressed over live Postgres in the world path), and **already emitted step-by-step** as the `views`
stack that the reasoning player renders. **v2 is: take that same DAG and serialize it as an inspectable
plan artifact, before/around executing it.**

> **What does NOT exist yet:** there is no `closure` / fixpoint / recursive primitive in `engine/`
> (grep confirms). Recursion is a *future extension* (§6), not a thing to expose today.

## 3. Architecture

```
User question
   │
   ▼
Sonnet orchestrator ──(parse NL, route, security, conversation)──┐
   │                                                             │
   │  Simple / single-hop  → prereasoner_query  (derive+execute together, as in v1)
   │  Complex / multi-hop   → prereasoner_plan   (derive the DAG, serialize it)  ── the v2 addition
   ▼                                                             │
PreReasoner: derive view DAG ──serialize──▶  PLAN ARTIFACT (Mermaid + JSON-DAG [+ Datalog])
   │            (ComposeEngine)                     │            │
   │  execute each node in dependency order         │            │
   ▼                                                ▼            ▼
PreReasoner: execute step 1 ─trace─▶ … ─▶ step N ─trace─▶ answer  │
                                                                  │
   the chat UI now shows TWO inspectable levels: the PLAN (was this the right decomposition?)
   and each STEP (did it compute correctly?) ───────────────────┘
```

**Call pattern (precise):**
- **Simple / single-hop:** the orchestrator calls `prereasoner_query` once — the plan is trivial (one
  step); derive-and-execute together, exactly as v1.
- **Complex / multi-hop:** the orchestrator calls `prereasoner_plan` first (returns the serialized DAG),
  then executes each node auditable — either by feeding step handles back to `prereasoner_query` or via a
  dedicated `prereasoner_execute_step`. The **plan call is the new thing**; the execution calls already
  exist.

Both the plan and each execution are derived, so both are auditable — the v2 claim.

## 4. New MCP tool: `prereasoner_plan`

The v2 addition. Same conventions as the v1 tools (`mcp-now.md` §2): **inline `tables`, no `dataset_id`,
identity passed through per `mcp-now.md` §5.** It derives the plan and returns it serialized — it does not
generate it.

**Input:** `question` (string), `tables` (array of `{name, data}`, inline).

**Output:**
- `plan`: the derived view DAG as a **JSON-DAG** — the executable intermediate. Each node names a primitive
  (`filter`, `group_agg`, `topn`, `world_join`, …), carries its args, and lists its input node(s) (the
  data-dependency edges, not just "next"). This is `ComposeEngine`'s plan, serialized.
- `plan_render`: the **human-viewable** form — a **Mermaid** flowchart of the reasoning the user can *see*
  (renders directly in the UI). Node labels are the same `label` strings the view stack already produces
  (`oplabel(op)` / the `label` field on each view).
- `steps`: an ordered / partially-ordered list of executable **step handles** the orchestrator feeds back
  one at a time to `prereasoner_query` (or `prereasoner_execute_step`).
- `derivation`: reason + alternatives + confidence for the decomposition itself (why these steps, what
  other decompositions scored lower). This is where the primitive-head activations (`PrimitiveReader`) and
  the pipeline-ordering choices are surfaced, so the *plan* carries the same audit metadata every other
  layer aspires to.

`prereasoner_query` from v1 remains, now optionally driven step-by-step from a `plan`.

> **Where `derivation` comes from (be honest about scope):** the primitive head already produces a
> pattern set with per-pattern signals inside `ComposeEngine._plan`; today those are consumed and not
> returned (same discard pattern as the resolution scores in `mcp-now.md` §4.3). Surfacing `derivation`
> is a scoped engine change — retain and serialize the primitive-head activations + the branch decisions
> `_plan` already makes — not new inference.

## 5. Plan format: Mermaid vs Datalog — investigate, then choose

The plan artifact should be **declarative, DAG-shaped, and well-represented in training data** so it is
legible and renderable — not because an LLM generates it (PreReasoner derives it), but because a trained-on
format is one humans and tools already read, and (for Mermaid) renders for free. **Run the investigation
below before committing** and pick one primary format (the other is a secondary lowering).

### The two candidates
- **Mermaid flowchart** — declarative, DAG-native, renders visually everywhere, heavily present in
  GitHub/docs training data. Its text *is* its structure. Weakness: it is a *diagram* language with no
  execution semantics — node labels must name primitives your executor understands. Best as the
  **human-facing plan surface**.
- **Datalog** — the cleanest declarative target for **multi-hop / recursive / transitive** steps (unbounded
  FK chains). Recursion and transitive closure are native. Present in training data (Soufflé, Datomic,
  CodeQL) but **thinner** than Mermaid. Best as the **executable lowering for recursive cases** (§6).

### Investigation task (do this first, report before choosing)
1. **Corpus representation** (The Stack / GitHub): count and sample for each format (Mermaid fenced blocks
   / `.mmd` / `flowchart|graph` directives; Datalog `.dl`/`.datalog`, Soufflé `.decl`/rules, Datomic query
   forms). Report raw counts, rough proportion, and **diversity** (distinct repos/domains, not just
   volume).
2. **Tokenizer coverage** for the current serving tokenizer: check each format's characteristic tokens
   (Mermaid `-->`, `[...]`, `flowchart TD`; Datalog `:-`, `.`-terminated rules, capitalized vars) tokenize
   cleanly (few tokens/construct, no pathological byte-splitting).
3. **Legibility test:** hand-render 5–10 of your actual view DAGs (use real ones from `world_compose`'s
   `views` output) in each format. Which reads more clearly *as a reasoning trace a non-expert can follow*?
4. **Dependency-structure fit:** confirm the chosen format expresses your DAG's **non-sequential data
   dependencies** (a step consuming another step's output). Mermaid edges must capture this; if some
   dependency can't be a simple flowchart edge, Mermaid is a *view* and the real executable is the
   JSON-DAG / Datalog.

### Decision rule (apply after the investigation)
- If Mermaid is far better represented, renders your DAGs legibly, **and** captures the dependency
  structure: **Mermaid is the primary human/tool-facing plan surface**, with the **JSON-DAG as the
  executable** and **Datalog as the lowering only for recursive/transitive steps** (§6).
- If multi-hop recursion turns out to dominate your target queries (SEC-filing / judicial multi-hop),
  weight Datalog higher as the executable and keep Mermaid as the rendered *view*.
- **Default expectation** (verify, don't assume): Mermaid as the rendered plan surface; JSON-DAG as the
  executable intermediate (it already exists — it's `ComposeEngine`'s plan); Datalog as the recursive
  lowering. Three representations of one derived plan, each at the right layer — analogous to
  SQL-as-bytecode.

Whatever you choose: **the LLM never generates the plan format.** PreReasoner derives the DAG and serializes
it. The format choice is about legibility and rendering, not generation fluency.

## 6. Executing the plan, and the recursion boundary

Once the plan artifact exists:
1. Execute each node **in dependency order**, each as an auditable step (the existing view execution,
   streamed to RTDB as `views/{i}` — `mcp-now.md` §0.5).
2. The chat UI now exposes **two inspection levels** (this is the v2 upgrade to the player in
   `mcp-now.md` §6): the **plan** (was this the right decomposition? — the rendered Mermaid DAG) *and* each
   **step** (did it compute correctly? — the SQL + resolution + result). Contrast with v1 in the UI: v1
   showed only the executed steps; v2 shows *the plan that chose them*, derived and inspectable.

**The recursion boundary (from ROADMAP Phase D/E).** Multi-hop over **bounded** FK chains lowers cleanly
and is what the engine does today (`world_join` chains, e.g. `city.country.continent` — see ARCHITECTURE
§7). **Genuinely recursive / unbounded-depth** steps (transitive closure) need a fixpoint. **This does not
exist in `engine/` yet** — there is no `closure` primitive. Adding it is the v2 frontier: isolate recursion
behind an explicit `closure(...)` primitive in the plan, keep the iteration visible in the trace, and use
**Datalog as the natural lowering** (recursion is native there). This is exactly where the format choice in
§5 interacts with the reasoning: the recursive cases are where Datalog earns its place.

---

## 7. Carry-over invariants (do not relax)

- **Derived, not generated** — the whole v2 claim. The plan is a serializer of `ComposeEngine`'s derived
  DAG. If at any point an LLM writes the plan, auditability collapses to v1's.
- **No separate explainability agent.** If reasoning lives in PreReasoner and is derived, it is auditable
  by construction and needs no narrator. Proposing one is a symptom that reasoning has leaked back into the
  LLM.
- Every layer emits **reason + alternatives + confidence** — now including the **plan** layer
  (`derivation`). Note this is a *scoped engine change* (retain the primitive-head signals `_plan` already
  computes), consistent with the same deferral called out for resolution scores in `mcp-now.md` §4.3.
- **Determinism where structure exists.** Plan derivation is deterministic (the *args* are Python; only the
  *pattern set* is read from the anchored head). Do not make the decomposition a learned/generated step
  beyond what the primitive head already does.
- **Orchestrator does selection/security/conversation; PreReasoner does reasoning + execution.** The moat
  is that the reasoning never leaves the auditable engine.

---

## 8. Done when

- `prereasoner_plan` returns a **derived** (not generated) reasoning DAG for a multi-hop question,
  serialized as a JSON-DAG + a renderable Mermaid view, with per-decomposition `derivation` metadata.
- The plan executes step-by-step, each step auditable, and the chat UI lets a user inspect **both** the
  plan and each step.
- The Mermaid-vs-Datalog investigation is documented (counts, tokenizer check, legibility, dependency fit)
  and a primary format is chosen with the recursive lowering identified.
- A recursive multi-hop question ("nth person in gold tier", a transitive FK chain) produces a plan whose
  `closure`/recursive step is explicit and whose fixpoint iteration is visible in the trace — **and the
  `closure` primitive it relies on has been added to `engine/` (it does not exist today).**
- Nowhere does an LLM generate the plan. The plan is derived and serialized; the LLM only orchestrates
  execution and speaks prose around the result.
