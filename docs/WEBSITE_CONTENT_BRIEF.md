## Glossary

| Idea | Customer wording | Developer wording | Boundary |
|---|---|---|---|
| Fields and relationships used to interpret the data | fields and their relationships | schema, typed dimensions, Schema.org classes and properties | A vocabulary is not itself the current answer data. |
| Figuring out what a column contains | identify what each column contains | typing, schema linking | Never imply every column is identified correctly. |
| Extra data used to interpret or link a value | reference data | reference tables, entity IDs, foreign keys | Distinguish public reference data from a user's private reference table. |
| Connecting related rows | link records by key | relational join, foreign-key path | Final row selection can use SQL joins; do not say embeddings are absent from the whole system. |
| Work performed to answer the question | calculation | typed query plan, SQL, validated candidate query | A visible query is not proof that the chosen query is correct. |
| What a user can inspect | query and source rows | execution trace, provenance | Do not use trace, derivation, and join path as interchangeable plain-English terms. |
| A request the system cannot answer | say when the data is not enough | clarification, abstention, refusal | Avoid promising that every unsupported case is caught. |
| Repeatability | same result with the same data and setup | deterministic execution | Fixed data, configuration, database state, and model artifacts are required. Determinism is not accuracy. |
